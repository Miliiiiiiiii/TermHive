> 自 2026-10-28 起施行。此前的做法（每次修改都前进一个版本号）不符合正规开发规范，已废止。

## 原则

**版本号只在发布点前进。** 开发过程中的每次改动不动版本号；版本号代表的是"对外发布的批次"，不是"第几次编译"。

**版本号变更以维护者明确指令为唯一触发（2026-10-30 增补）。** 没有维护者（gordo）明确说要升级版本或发版，任何情况下都不改版本号——包括正式号（`release:patch/minor`）、rc 预发布号、以及任何"为了给真机装包"的变通升号。认为需要新的构建号时，先说明理由，等维护者确认后再动。

## 版本号语义（semver）

`MAJOR.MINOR.PATCH`，当前处于 `0.x` 开发期：

| 段 | 何时前进 | 示例 |
|---|---|---|
| MINOR | 一个**规划好的功能批次**发布（先在 ROADMAP 里立项） | 0.1.0 → 0.2.0（日志模式 + 文件预览批次） |
| PATCH | 一批**修复/小调整**发布 | 0.1.0 → 0.1.1 |
| MAJOR | 1.0.0：功能集与数据格式稳定 | — |

## 中间验证构建（预发布号）

开发中途需要真机验证时，用**预发布后缀**，不占用正式版本号：

```
0.2.0-rc.1  →  0.2.0-rc.2  →  …  →  0.2.0（正式发布）
```

- rc 号只在同一目标版本内递增（`rc.1`、`rc.2`…），正式发布落回无后缀的 `0.2.0`；
- **命名定论（2026-10-28 维护者定案）：沿用 `rc`**。曾对比 snapshot（同名覆盖式，DBX 按版本目录 + sha256 校验装不下，且无法区分构建）与 `-dev.N`（语义相同、名字更"开发中"）——rc 胜出：semver 标准预发布标记，且在 0.x 阶段它只表示"第 N 个开发验证构建"，不承诺功能完成度；
- 已验证打包器接受该格式（2026-10-28 实测 `0.9.0-rc.1` 打包成功）；客户端对 rc 版本的安装与升级排序还需一次真机实测确认，若客户端拒绝则回退方案：中间验证构建一律本地测试（e2e/proto），真机验证攒到发布点；
- CHANGELOG 里 rc 构建只在对应正式版本的条目下记一行"rc 验证记录"，不单独成条；
- rc 号同样是版本号变更：打 rc 也需要维护者明确同意（见"原则"），不得因"要给真机验证"自行升号。

## 发版流程（唯一合法的版本变更方式）

```bash
# 1. 在 CHANGELOG.md 写好下一版的 ## [x.y.z] 条目（脚本会强制校验存在）
# 2. 执行发版：
npm run release:patch   # 或 npm run release:minor
# 3. 脚本做的事：校验 CHANGELOG 有对应条目 → 一致地升 manifest.json 与 backend/main.go → 输出核对清单
# 4. 人工执行：npm test && npm run package
# 5.（仓库建立后）打 git tag x.y.z 并推送
```

## 门禁（防再犯）

`npm run check`（CI 同样执行）包含两项硬校验：

1. `check-version.mjs`：manifest.json 与 backend/main.go 的版本必须一致（历史事故：只改一半导致 sidecar 拒载）；
2. `check-changelog.mjs`：CHANGELOG.md 必须存在**当前版本**的条目——版本前进了却没有变更记录，直接失败。

任何绕过脚本手改版本号的行为都视为违规。

## 与 DBX 平台约束的关系

DBX 按版本号目录安装插件（`plugins/<id>/versions/<ver>/`）且逐文件 sha256 校验——"改了代码但版本没变"的包无法体现为新版本。这不是版本管理要求每次改动都发版，而是**只有发版才需要打安装包**：日常开发在本地测试（e2e/proto/单测），需要真机验证时用 rc 号，正式包只在发布点打。
